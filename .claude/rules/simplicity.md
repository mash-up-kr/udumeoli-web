# 과설계 방지 (Lazy Senior Dev)

최고의 코드는 안 쓴 코드다. [behavior.md](behavior.md) "Simplicity First"를 순서와 판단 기준으로 구체화한다. 정확성·보안·접근성보다 우선하지 않는다 (아래 "게으르면 안 되는 것").

## 코드 작성 전 사다리

문제를 이해하고 실제 흐름을 끝까지 읽은 뒤, 멈출 수 있는 첫 단계에서 멈춘다. 두 단계가 다 되면 더 높은 단계를 택한다.

1. 진짜 필요한가? (YAGNI) 아직 없는 요구사항이면 스킵하고 한 줄로 이유를 남긴다.
2. 이미 코드베이스에 있나? `src/shared` 유틸·훅, shadcn/ui, 기존 패턴부터 찾는다. 몇 파일 건너에 있는 걸 다시 만드는 게 가장 흔한 slop이다.
3. 표준 라이브러리/런타임(TS/Web API)이 하나? 그걸 쓴다.
4. 네이티브 플랫폼 기능이 커버하나? `<input type="date">` > 커스텀 피커, CSS > JS, HTML 시맨틱 > `role` 땜빵.
5. 설치된 의존성이 푸나? 몇 줄이면 되는 걸로 새 패키지 추가 금지.
6. 한 줄로 되나? 한 줄로 한다.
7. 그래도 안 되면 최소한의 코드를 짠다.

## 버그 수정 = 증상이 아니라 원인

- 고치기 전에 건드릴 함수의 호출자를 전부 grep한다. 티켓이 지목한 경로만 패치하면 형제 호출자는 깨진 채 남는다.
- 공유 지점 한 곳을 고치는 게 호출자마다 가드를 넣는 것보다 diff가 작다. 예: `Calendar`가 `classNames`를 슬롯째 덮어써 호출부마다 우회하던 문제를 컴포넌트 내부 `cn()` 병합 한 번으로 해결 (PR #75).
- "원인 vs 증상" 판단은 [good-debug](../skills/good-debug/SKILL.md), 수정 위치(호출자 전부 vs 공유 지점 한 곳)는 여기.

## 규칙

- 요청받지 않은 추상화 금지: 구현체 하나뿐인 인터페이스, 상품 하나뿐인 팩토리, 안 바뀌는 값의 config.
- 요청받지 않은 새 의존성 금지.
- "나중을 위한" 보일러플레이트 금지.
- 추가보다 삭제. 클레버보다 뻔함. 파일 수 최소.
- 가장 짧은 동작하는 diff가 이긴다. 단, 문제를 이해한 다음에만. 엉뚱한 자리의 최소 변경은 버그를 하나 더 만든다.
- 복잡한 요청은 되묻는다: "진짜 X 필요한가, Y로 되지 않나?"
- 크기 같은 stdlib 방식 둘 중엔 edge case가 정확한 쪽.
- 의도적 단순화(글로벌 락, O(n²) 스캔, 나이브 휴리스틱)는 `ponytail:` 주석으로 한계와 업그레이드 시점을 남긴다. 예: `// ponytail: 글로벌 락, 처리량 문제되면 계정별 락으로`

## 게으르면 안 되는 것

- 문제 이해. 흐름을 끝까지 안 읽고 작은 diff부터 내미는 건 게으름이 아니라 위험한 확신.
- 신뢰 경계(사용자 입력, 외부 API) 검증.
- 데이터 손실을 막는 에러 핸들링.
- 보안, 접근성 ([good-a11y](../skills/good-a11y/SKILL.md)).
- 명시적으로 요청받은 것.
- 분기·반복·파서·금액/보안 로직은 실행 가능한 확인 하나(assert self-check 또는 작은 테스트)를 남긴다. 프레임워크·픽스처 불필요. 한 줄짜리는 테스트 불필요.
