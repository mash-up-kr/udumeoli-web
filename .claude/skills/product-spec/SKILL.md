# 서비스 기획 관리

공통 원본은 `docs/product/`이다. Claude와 Codex 모두 같은 파일을 읽고 수정한다.

## 기획 탐색과 개발 검토

`docs/product/README.md`의 검색어·화면·문서 ID로 관련 기획을 고른다. 필요하면 `rg -n '검색어' docs/product`로 찾는다. 해당 화면의 항목과 관련 Q를 읽고 계획·구현·리뷰 근거에 SPEC ID/항목 번호를 남긴다. 연결 플로우와 기존 코드 경로도 확인한다. 코드가 이미 그렇게 되어 있다는 이유로 기획을 변경하지 않는다.

## 대화에서의 갱신

- 명시적 확정/변경 요청: 재확인 없이 요청 범위의 정책 본문, 변경 이력, 관련 Q의 결정·상태, 연계 문서를 함께 갱신한다. 사용자가 이번에 확정하지 않은 문제까지 해결 처리하지 않는다.
- 아이디어/질문/가정 또는 기존 기획과 다른 제안: 기존 정책과 제안, 영향 문서, 구현 영향을 짧게 보여주고 “이 내용으로 기획 문서를 변경할까요?”라고 묻는다. 답이 없으면 정책은 유지한다.
- 결론 없는 논의: 열린 Q로 기록한다. 사용자가 기록 자체를 원하지 않으면 만들지 않는다. 정책 승인 대기는 영향을 받는 구현에만 적용한다.
- 변경 기록: 날짜, 변경 전후, 사용자 결정의 대화 요지, 영향 항목을 남긴다. 대화가 제공하지 않은 인용·메시지 ID·승인 날짜를 만들어내지 않는다. 사용자 확정 내용과 원문 사본을 구분하며 Figma 미반영이면 표시한다.

## Figma 추출과 재확인

1. URL의 file key·node ID를 보존한다. Figma MCP로 본문을 읽고 원문 항목 번호, 조건, 수치, 오류, 권한, 문구를 빠짐없이 정리한다. 텍스트가 잘리거나 주변 디자인 참조가 필요하면 해당 노드와 스크린샷을 추가로 확인한다. 도구가 요구하는 Figma 스킬을 먼저 읽는다.
2. 원문 표기일과 실제 확인일을 분리한다. 원문에 없거나 읽지 못한 내용을 추측해 채우지 않는다. 각 노드 문서와 인덱스에 연결한다.
3. 재확인 시 기존 사용자 확정 변경을 포함해 차이를 비교한다. 의미가 같은 문서 정리와 출처 보강은 진행하되 정책 충돌은 질문한다. 승인 없이 Figma·코드 중 하나를 정답으로 선택하지 않는다.
4. 접근 실패면 기존 사본을 유지하고 미확인 노드를 보고한다. 실제 읽지 않은 문서의 확인일은 바꾸지 않는다. Figma에 쓰는 작업은 별도 요청이 없는 한 수행하지 않는다.

## 미확정 관리와 검증

`OPEN_QUESTIONS.md`에 새 고유 Q ID, 열림/해결/보류 상태, 원문 미확정/충돌/미기재 구분, 영향 화면 링크, 근거 항목, 결정 질문을 기록한다. 해결되면 결정 내용·날짜·근거와 영향 문서를 함께 갱신하고 질문 이력은 유지한다.

문서 변경 후 `pnpm spec:check`와 diff 확인으로 상대 링크·SPEC/Q 참조·원문 매핑을 검증한다. 이 검사는 원문 의미나 결정 근거의 정확성을 대신하지 않는다. 문서만 바꿨다면 앱 빌드가 필요한 것은 아니다. 코드도 바뀌면 프로젝트의 기존 검증 규칙을 적용한다. 보고에는 변경 문서, 확정 사항, 남은 질문, 실행한 검증을 구분한다.
