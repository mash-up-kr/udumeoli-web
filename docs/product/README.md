## 문서 사용과 최신화

1. 개발 전에 적용 문서 ID·항목 번호와 관련 Q 번호를 확인하고 구현 조건에 반영한다.
2. 정책이 불명확하거나 기획·대화·코드가 충돌하면 차이를 제시하고 해당 결정만 묻는다. 독립적인 작업은 계속한다.
3. 사용자가 정책을 명시적으로 확정·변경 요청하면 해당 문서와 Q 상태·이력을 같은 작업에서 갱신한다. 단순 아이디어·질문·가정은 승인으로 취급하지 않는다.
4. 논의로 변경 가능성이 생기면 “기존 A를 B로 기획 문서에 반영할까요?”처럼 문서와 변경점을 특정한다. 이미 명시적으로 요청한 변경은 재승인받지 않는다.
5. 확인되지 않은 제안은 Q로 기록하고 현행 정책을 덮어쓰지 않는다. Figma와 Markdown 차이가 생기면 문서에 차이와 확정 근거를 기록한다.
6. 개발 완료 시 실제 동작·예외·권한을 해당 항목과 대조하고 적용 기획, 검증 결과, 남은 Q를 보고한다.

기획 갱신 절차는 [공통 스킬](../../.claude/skills/product-spec/SKILL.md), 자동 참조 기준은 [공통 규칙](../../.claude/rules/product-spec.md)에 있다. AI 세션에서 규칙을 따르는 방식이며 Figma 변경 자동 감지나 백그라운드 동기화는 아니다. 원문 재확인은 Figma 접근이 가능한 세션에서 수행하며 확인한 노드만 확인일을 갱신한다.

## 기존 스펙과의 관계

- [MAP_SPEC.md](../../MAP_SPEC.md): 2026년 7월의 다른 노드에서 추출한 지도 정책과 구현 메모. 이번 문서와 겹치지 않는 내용은 참고하며, 상충하는 정책은 Q05처럼 확인 후 정리한다. 이번 정리만으로 과거 사용자 결정을 폐기하지 않는다.
- [GOOGLE_MAPS_SPEC.md](../../GOOGLE_MAPS_SPEC.md): 지도 이식 당시의 기술·구현 가이드. 현행 제품 정책과 구현 사실을 구분한다.
- 근거 우선순위: 해당 정책에 대한 명시적 사용자 확정 결정 → 상충하지 않는 원문 기획. 결정 시점·범위가 불분명하거나 두 원문이 충돌하면 임의로 최신 날짜만 보고 선택하지 않는다.

## 기록 형식

문서 수정 후 `pnpm spec:check`로 상대 링크·Q 참조·원문 노드 중복·인덱스 등록·공통 진입점 연결을 검사한다. 정책의 의미적 정확성이나 Figma 변경 여부를 자동 판정하는 검사는 아니다.

화면 문서에는 문서 ID, 출처 노드·링크, 원문 표기일, 확인일, 상태, 정책 항목, 관련 Q, 변경 이력을 유지한다. 사용자가 변경한 정책은 해당 항목 아래에 `사용자 확정 (날짜): 이전 → 변경 / 근거 요지 / Figma 반영 대기 여부`를 남겨 원문과 구분한다. 정책 재구성 후에도 원래 항목 번호를 유지한다.

열린 문제는 [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md)에 Q ID, 상태, 구분, 영향 문서, 근거, 질문, 결정을 남긴다. 관련 화면에서 Q를 역링크하고 인덱스도 함께 갱신한다.
